项目简介

极速购 AI 客服系统是一个电商平台智能客服项目，模拟了真实电商场景下的客服对话系统。项目通过 四个递进式模块，完整展示了从最基础的大模型对话，到 RAG 知识库问答、Agent 工具调用，最终到 LangGraph 多节点协作的 AI 应用开发全流程。

每个模块都有独立的前端页面和后端接口，可以独立运行和体验，非常适合作为前端工程师学习 AI 应用开发的入门实战项目。

为什么这个项目适合你？

  • 前端技术栈熟悉：使用 Vue 3 + Vite，降低学习 AI 概念时的前端认知负担
  • AI 概念递进式引入：从最简单的 Prompt → Model 链式调用，逐步深入到 RAG、Agent、Graph
  • 覆盖 AI 应用核心范式：当前业界 AI 应用四大主流范式（对话、RAG、Agent、Workflow）全部覆盖
  • 生产级架构设计：SSE 流式输出、向量数据库、意图路由等都是真实生产环境中的技术方案
  • 代码量适中：总代码量约 2000 行，核心逻辑清晰，没有冗余的样板代码

一、入门知识：AI 应用开发基础概念

在深入项目代码之前，先理解几个核心概念。这些概念是整个项目的地基。

1.1 LLM（大语言模型）是什么？

LLM（Large Language Model）是一种通过海量文本训练出来的 AI 模型，它能理解和生成人类语言。你可以把它理解为一个「超级文本续写器」——给它一段文字开头，它能预测接下来最可能出现的文字。

本项目使用的 DeepSeek 就是一个 LLM。它兼容 OpenAI 的 API 协议，所以在代码中可以直接用 ChatOpenAI 类来调用，只需要把 baseURL 改成 DeepSeek 的地址即可。

// 这就是调用大模型的核心代码，非常简洁
import { ChatOpenAI } from '@langchain/openai';

const model = new ChatOpenAI({
  model: 'deepseek-chat',
  apiKey: process.env.DEEPSEEK_API_KEY,
  configuration: {
    baseURL: 'https://api.deepseek.com/v1',  // 只换这一行
  },
});

1.2 Prompt（提示词）是什么？

Prompt 是你给大模型的输入指令。就像跟人说话一样，你说得越清楚，对方回答越好。在 AI 应用中，Prompt 通常由三部分组成：

  • System Prompt：设定角色和规则（"你是客服助手，只能回答购物问题"）
  • Chat History：之前的对话历史，让模型有"记忆"
  • User Input：用户当前的问题

项目中使用 ChatPromptTemplate 来管理 Prompt 模板，支持变量插值：

ChatPromptTemplate.fromMessages([
  ['system', '你是极速购客服助手。当前时间：{current_time}'],
  ['placeholder', '{chat_history}'],  // 对话历史占位符
  ['human', '{user_input}'],          // 用户输入
]);

1.3 Temperature（温度参数）

Temperature 控制模型输出的随机性，取值范围 0~2：

值效果适用场景
0确定性最强，每次回答几乎一样意图分类、工具调用、RAG 检索
0.5适度随机，回答有一定变化但不跑偏客服回复、答案整合
0.7较有创意，回答多样通用闲聊

项目中不同模块使用了不同的 temperature，这是很重要的工程细节：需要精确的场景用低温度，需要灵活的场景用高温度。

1.4 Token 与上下文窗口

大模型按 Token 计费和处理文本。1 个 Token 大约等于 0.75 个英文单词或 0.5 个中文字。每个模型有上下文窗口限制（如 DeepSeek 支持约 64K Token），超过限制的内容会被截断。

项目中对历史消息做了截断处理，只传最近 10 条消息：

// 取最近 10 条历史，避免 Token 超限
const history = messages.value.slice(-10);

1.5 SSE（Server-Sent Events）流式输出

SSE 是一种 HTTP 长连接技术，服务器可以持续推送数据给客户端，而不需要客户端反复请求。在 AI 应用中，SSE 用于实现逐字输出效果——大模型生成一个字就推送给前端一个字，用户体验远好于等全部生成完再返回。

后端实现（Express 设置 SSE 响应头）：

res.setHeader('Content-Type', 'text/event-stream; charset=utf-8');
res.setHeader('Cache-Control', 'no-cache');
res.setHeader('Connection', 'keep-alive');
res.setHeader('X-Accel-Buffering', 'no'); // 禁用 Nginx 缓冲

// 逐块发送
const sendData = (data) => {
  res.write(`data: ${JSON.stringify(data)}\n\n`);
};

前端实现（使用 Fetch + ReadableStream 读取）：

const response = await fetch(url, { method: 'POST', body: ... });
const reader = response.body.getReader();
const decoder = new TextDecoder('utf-8');

while (true) {
  const { done, value } = await reader.read();
  if (done) break;

  const text = decoder.decode(value, { stream: true });
  const lines = text.split('\n').filter(l => l.startsWith('data: '));

  for (const line of lines) {
    const parsed = JSON.parse(line.slice(6));
    if (parsed.content) {
      streamText.value += parsed.content; // 逐字追加
    }
  }
}
为什么不用 WebSocket？
SSE 是单向通信（服务器→客户端），更简单、更轻量。AI 对话场景只需要服务器推送文本，不需要双向通信，所以 SSE 是最佳选择。WebSocket 适合需要客户端也能实时推送的场景（如聊天室）。

二、LangChain 核心概念

LangChain 是目前最流行的 AI 应用开发框架，它把 AI 应用的各个组件抽象成可组合的模块。理解 LangChain 的核心抽象是理解本项目代码的关键。

2.1 LCEL（LangChain Expression Language）

LCEL 是 LangChain 的管道语法，用 |（在 JS 中是 .pipe()）将多个组件串联起来，就像 Unix 管道一样。数据从左到右流经每个组件，上一个组件的输出自动成为下一个组件的输入。

最基本的 LCEL 链：

// Prompt → Model → OutputParser
const chain = prompt.pipe(model).pipe(parser);

// 调用时传入变量
const result = await chain.invoke({
  user_input: '你好',
  chat_history: [],
  current_time: new Date().toLocaleString('zh-CN'),
});

2.2 Runnable 接口

LCEL 中所有组件都实现了 Runnable 接口，提供统一的调用方法：

方法用途项目中的使用
invoke()一次性调用，返回完整结果Agent 查询、RAG 查询、意图分类
stream()流式调用，逐块返回结果基础对话 SSE 流式输出
batch()批量调用本项目未使用

这就是为什么同一个 Chain 可以支持流式和非流式——只需选择 invoke 还是 stream。

2.3 RunnableSequence 与 RunnablePassthrough

在 RAG Chain 中用到了更复杂的 Runnable 组合：

// RunnableSequence：显式定义执行序列
export const ragChain = RunnableSequence.from([
  {
    context:  (input) => retriever.pipe(formatDocs).invoke(input.question),
    question: (input) => input.question,
  },
  ragPrompt,
  model,
  new StringOutputParser(),
]);

第一个参数是一个对象映射，它的每个字段是一个函数，并行执行后结果合并为一个新对象传给下一步。这里 context 字段先检索文档再格式化，question 字段直接透传。

RunnablePassthrough.assign() 则用于在不丢失原始输入的基础上追加字段：

// 在输入上追加 docs 字段，保留原始 question
RunnablePassthrough.assign({
  docs: (input) => retriever.invoke(input.question),
})

2.4 ChatPromptTemplate

LangChain 的 Prompt 模板系统，支持三种消息类型：

类型含义模板中的写法
system系统消息，设定角色和规则['system', '你是客服助手...']
human用户消息['human', '{user_input}']

花括号 {} 中的是变量名，调用 invoke() 时传入对应的值即可替换。

三、RAG（检索增强生成）原理

问题背景：大模型的知识停留在训练数据截止日期，不了解你的私有数据（如公司产品手册、售后政策）。如果直接问大模型"蓝牙耳机 X1 Pro 的续航是多少"，它要么不知道，要么编造答案。

RAG 解决方案：先从你的知识库中检索相关文档片段，然后把检索到的内容和用户问题一起喂给大模型，让模型基于检索到的内容来生成回答。这样模型就能回答私有数据问题了，而且有据可查。

3.2 关键概念详解

Embedding（文本向量化）

Embedding 是把文本转换成高维向量（一组数字）的过程。语义相近的文本，向量距离也近。例如"蓝牙耳机续航"和"蓝牙耳机能用多久"的向量距离很近，但"蓝牙耳机续航"和"退货政策"的向量距离很远。

本项目使用智谱 AI 的 embedding-3 模型，将文本转为 1536 维向量：

import { OpenAIEmbeddings } from '@langchain/openai';

export const embeddings = new OpenAIEmbeddings({
  model: 'embedding-3',
  apiKey: process.env.ZHIPU_API_KEY,
  configuration: {
    baseURL: 'https://open.bigmodel.cn/api/paas/v4',
  },
});

TextSplitter（文本切分）

为什么要切分？因为一篇长文档整体向量化后语义会被稀释。切成小段落（chunk），每个 chunk 聚焦一个主题，检索更精准。

const splitter = new RecursiveCharacterTextSplitter({
  chunkSize: 500,      // 每个 chunk 最多 500 字符
  chunkOverlap: 50,    // 相邻 chunk 重叠 50 字符，避免语义断裂
});

RecursiveCharacterTextSplitter 会递归地按段落 → 句子 → 字符的层级切分，尽量保持语义完整。

PGVector（向量数据库）

pgvector 是 PostgreSQL 的向量扩展插件，让 PostgreSQL 支持向量类型和相似度检索。相比独立的向量数据库（如 Pinecone、Milvus），pgvector 的优势是可以和现有 PostgreSQL 基础设施无缝集成。

-- 向量表结构
CREATE TABLE knowledge_embeddings (
  id        bigserial PRIMARY KEY,
  content   text,          -- 原始文本
  metadata  jsonb,         -- 元数据（来源文件名等）
  embedding vector(1536)   -- 1536 维向量
);

检索时使用余弦相似度（<=> 操作符）找最相似的 Top-K 个文档：

// LangChain 封装了检索逻辑
const retriever = vectorStore.asRetriever({ k: 4 }); // 返回最相似的 4 个 chunk

四、Agent（智能体）原理

问题背景：大模型本身只能生成文本，不能执行实际操作。如果用户问"我的订单 ORD-001 发货了吗？"，大模型无法查询数据库，只能猜测或拒绝回答。

Agent 解决方案：给大模型配备工具（Tools），让模型能调用外部函数获取真实数据。Agent 会根据用户问题自动决定调用哪个工具、传什么参数，拿到工具返回结果后再组织自然语言回答。

4.1 ReAct 模式

ReAct = Reasoning + Acting，即"推理+行动"循环：

用户
问题
→
Thought
思考该做什么
→
Action
调用工具
→
Observation
观察工具返回
↻

最终回答

模型会循环执行 Thought → Action → Observation，直到收集到足够信息才输出最终 Answer。LangGraph 的 createReactAgent 封装了这个循环逻辑。

4.2 Tool（工具）定义

每个工具包含三要素：名称、描述、参数 Schema。模型通过描述来判断何时使用哪个工具，通过 Schema 来知道该传什么参数。

import { tool } from '@langchain/core/tools';
import { z } from 'zod';

export const getOrderInfoTool = tool(
  async ({ orderId }) => {
    // 实际查询逻辑
    const order = orders[orderId];
    return JSON.stringify(order);
  },
  {
    name: 'getOrderInfo',
    description: '根据订单号查询订单详情...当用户询问订单状态时调用。',
    schema: z.object({
      orderId: z.string().describe('订单号，格式为 ORD-xxx'),
    }),
  }
);
Zod Schema 的重要性
z.string().describe(...) 中的 describe 不是给开发者看的，而是给大模型看的。模型通过这个描述来理解参数的含义和格式，从而正确提取参数值。

五、LangGraph 原理

问题背景：前面的 Agent 只能调用工具，无法根据问题类型走不同处理流程。比如用户问"退款政策"应该走知识库检索，问"我的订单"应该走 Agent 工具调用，闲聊应该直接用 LLM 回答。如何让系统自动选择正确的处理路径？

LangGraph 解决方案：用有向图编排工作流。每个节点是一个处理步骤，边定义了执行顺序，条件边可以根据状态动态路由。这就构成了一个状态机，数据在图中流动，每个节点读取和更新共享状态。

5.3 Annotation（状态注解）

LangGraph 使用 Annotation 来定义状态结构，每个字段指定一个 reducer（合并策略）：

export const GraphState = Annotation.Root({
  ...MessagesAnnotation.spec,  // 自动包含 messages 字段

  userInput: Annotation({
    reducer: (_, next) => next,  // 直接覆盖
    default: () => '',
  }),

  intent: Annotation({
    reducer: (_, next) => next,  // 直接覆盖
    default: () => '',
  }),

  orderResult: Annotation({

export function useChat() {
  const messages = ref([]);       // 完整消息历史
  const streaming = ref(false);   // 是否正在流式输出
  const streamText = ref('');     // 当前流式输出的文本

  const sendMessage = async (userInput, scrollCallback) => {
    // 1. 把用户消息加入历史
    messages.value.push({ role: 'user', content: userInput });

    // 2. 发起 SSE 请求
    const response = await fetch(`${API_BASE}/chat/stream`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify({ message: userInput, history }),
    });

    // 3. 读取流
    const reader = response.body.getReader();
    const decoder = new TextDecoder('utf-8');

    while (true) {
      const { done, value } = await reader.read();
      if (done) break;

      const lines = decoder.decode(value, { stream: true })
        .split('\n').filter(l => l.startsWith('data: '));

      for (const line of lines) {
        const parsed = JSON.parse(line.slice(6));
        if (parsed.content) {
          streamText.value += parsed.content;  // 逐字追加
          await nextTick();
          scrollCallback?.();
        }
      }
    }

    // 4. 流结束，存入历史
    messages.value.push({ role: 'assistant', content: streamText.value });
  };

  return { messages, streaming, streamText, error, sendMessage, clearMessages };
}

2.2 RAG Chain 组装

// 初始化向量存储（模块加载时执行一次）

  {

    context:  (input) => retriever.pipe(formatDocs).invoke(input.question),
    question: (input) => input.question,

  ragPrompt,   // 注入 context + question
  model,       // LLM 生成
  new StringOutputParser(),
]);

// 带来源信息的 RAG Chain（额外返回引用的文档）
export const ragChainWithSources = RunnableSequence.from([
  // 先检索文档，存入 input.docs
  RunnablePassthrough.assign({ docs: (input) => retriever.invoke(input.question) }),
  {
    // 用检索到的文档生成回答
    answer: RunnableSequence.from([
      (input) => ({ context: formatDocs(input.docs), question: input.question }),
      ragPrompt, model, new StringOutputParser(),
    ]),
    // 同时提取来源信息
    sources: (input) => input.docs.map((doc) => ({
      content: doc.pageContent.slice(0, 100) + '...',
      source:  doc.metadata.source,
    })),
  },
]);

两个 Chain 的区别：ragChain 只返回答案；ragChainWithSources 同时返回答案和引用来源，前端可以展示"参考来源"标签。

  const steps = [];
  for (let i = 0; i < msgs.length; i++) {
    if (msgs[i].tool_calls?.length) {
      for (const tc of msgs[i].tool_calls) {
        steps.push({
          tool: tc.name,
          input: tc.args,
          obs: msgs[i + 1]?.content ?? '',
        });
      }
    }
  }

  return { orderResult: { answer: finalMsg.content, steps } };
};

关键设计：这个 Agent 的 Prompt 说"只查数据，不生成最终回答"，因为最终回答由 answerSynthesizer 节点统一生成。这就是关注点分离——每个节点只做自己的事。

4.5 答案整合节点

export const answerSynthesizerNode = async (state) => {
  const { userInput, orderResult, ragResult, finalAnswer, intent } = state;

  // general 意图已在 generalChatNode 生成答案，直接透传
  if (intent === 'general' && finalAnswer) return { finalAnswer };

    userInput,
    orderResult: orderResult ? JSON.stringify(orderResult.answer) : '无',
    ragResult:   ragResult   || '无',
  });
  return { finalAnswer: result };
};

这是整个图的汇合点，负责把前面节点的查询结果整合成用户友好的回答。对于 general 意图直接透传，避免重复调用 LLM。

项目难点与亮点

项目难点

难点一：SSE 流式输出的全链路实现

从后端 LangChain stream() → Express res.write() → 前端 ReadableStream → Vue 响应式更新，涉及三层流式传递。每一层都有坑：

  • 后端：必须设置 X-Accel-Buffering: no 禁用 Nginx 缓冲，否则流会被攒在一起一次性发送
  • 传输：SSE 格式严格要求 data: \n\n，少了换行会导致前端解析失败
  • 前端：decoder.decode(value, { stream: true }) 的 stream: true 参数必须加，否则多字节字符（如中文）可能被截断
  • 渲染：每次追加文本后需要 nextTick() 再滚动，否则 DOM 还没更新

难点二：RAG 向量入库与检索的完整链路

  • 环境依赖：需要安装 Docker + PostgreSQL + pgvector，配置端口不冲突，创建数据库和扩展
  • Embedding 模型选择：智谱 AI 和阿里云百炼的 API 接口不同，需要正确配置 baseURL 和 model 名称
  • chunkSize 调优：切分太大检索不精准，太小语义不完整，需要根据文档特点调整
  • 向量维度匹配：入库脚本中的 vector(1536) 必须和 Embedding 模型输出维度一致

难点三：LangGraph 条件路由与状态管理

  • 状态设计：需要预判哪些字段需要跨节点共享，合理设计 GraphState
  • Reducer 理解：(_, next) => next 表示覆盖更新，如果需要累加需用不同的 reducer
  • 意图分类的稳定性：模型可能返回意外内容，需要做兜底处理
  • streamMode 选择：updates vs values vs messages 的区别和使用场景

难点四：Agent 消息数组的解析

Agent 执行后返回的 messages 数组结构复杂，需要正确识别哪些消息包含 tool_calls，哪条是工具执行结果，哪条是最终回答：

  AIMessage("亲，您的订单 ORD-001 已发货..."),  // index 3: 最终回答

请介绍一下你的 AI 客服项目，用了什么技术栈？

这是一个电商平台 AI 智能客服系统，前端用 Vue 3 + Vite，后端用 Node.js + Express，AI 框架用的是 LangChain.js 和 LangGraph.js，大模型用的 DeepSeek，向量数据库用 PostgreSQL + pgvector。

项目分四个递进模块：基础对话用 LCEL 管道实现 Prompt → Model → Parser 链式调用；RAG 知识库把商品手册和售后政策向量化存入 pgvector，实现基于私有数据的问答；Agent 模块用 ReAct 模式让 LLM 自主调用订单查询工具；LangGraph 中枢用状态图编排意图路由 → 多节点协作 → 答案整合的完整工作流。所有模块都支持 SSE 流式输出。

回答技巧：先说技术栈，再说四个模块的核心能力，最后点出 SSE 流式这个亮点。30 秒内说清楚，不要展开细节。

LCEL 是什么？你是怎么用的？

LCEL（LangChain Expression Language）是 LangChain 的管道语法，用 .pipe() 方法把多个组件串联起来，类似 Unix 管道。数据从左到右流经每个组件，上一个的输出自动成为下一个的输入。

项目中的基础用法是 prompt.pipe(model).pipe(parser)，非常直观。在 RAG Chain 中用了更复杂的 RunnableSequence.from()，它可以传入一个对象做并行映射——比如同时检索文档和透传问题，然后再交给 Prompt。还用了 RunnablePassthrough.assign() 来在不丢失原始输入的基础上追加字段。

LCEL 的好处是所有组件都实现了 Runnable 接口，统一支持 invoke、stream、batch 三种调用方式。同一个 Chain 想从非流式改成流式，只需要把 invoke 换成 stream 就行。

SSE 流式输出是怎么实现的？前后端各做了什么？

后端：Express 路由设置四个 SSE 响应头——Content-Type: text/event-stream、Cache-Control: no-cache、Connection: keep-alive、X-Accel-Buffering: no。最后一个很重要，禁用 Nginx 缓冲，否则流会被攒在一起。然后调用 LangChain Chain 的 stream() 方法，用 for await 逐块获取，每块用 res.write('data: ' + JSON.stringify(data) + '\\n\\n') 发送。

前端：不能用普通的 fetch().then()，要用 response.body.getReader() 获取 ReadableStream，配合 TextDecoder 解码。关键细节是 decoder.decode(value, { stream: true }) 的 stream: true 必须加，否则多字节中文字符可能被截断。然后按行 split，过滤 data: 开头的行，JSON.parse 后追加到响应式变量。

渲染：用 Vue 的 ref 存储 streamText，每次追加后 nextTick 触发滚动，用 CSS @keyframes blink 做闪烁光标效果。

RAG 的流程是什么？为什么需要 RAG？

RAG 是 Retrieval-Augmented Generation 的缩号，检索增强生成。需要 RAG 是因为大模型的训练数据有截止日期，不了解私有数据。如果直接问大模型"蓝牙耳机 X1 Pro 的续航"，它会编造答案，这就是幻觉问题。

RAG 分两个阶段：入库阶段先执行一次，读取 Markdown 文档，用 RecursiveCharacterTextSplitter 切分成 500 字符的 chunk（重叠 50 字符避免语义断裂），然后用 Embedding 模型向量化存入 pgvector。查询阶段每次提问时执行，先把用户问题向量化，在 pgvector 中做余弦相似度检索取 Top-4，把检索到的文档片段和用户问题一起拼入 Prompt，让模型基于检索内容生成回答。

项目还实现了来源追溯——用 RunnablePassthrough.assign 在不丢失原始输入的基础上追加 docs 字段，最终返回答案的同时返回引用的文档来源，前端展示"参考来源"标签。

防幻觉的关键是 Prompt 中加了"如果知识库中没有相关内容，请如实告知用户，不要编造信息"这句话。

chunkSize 和 chunkOverlap 怎么选？太大太小有什么问题？

chunkSize 控制每个文本块的大小。太大会导致一个 chunk 包含多个主题，检索时语义不聚焦，匹配不精准；太小会导致单个 chunk 语义不完整，模型生成回答时缺少上下文。项目用的是 500 字符，对于商品介绍和政策文档这种结构化内容比较合适。

chunkOverlap 控制相邻 chunk 的重叠区域。作用是防止切分时刚好把一句话或一个段落从中间截断，导致语义丢失。项目用 50 字符（chunkSize 的 10%），这是一个常见的经验值。

实际项目中需要根据文档类型调整：技术文档可能需要更大的 chunk（1000+）保留代码完整性，FAQ 类文档可以更小（200-300）让每个 chunk 就是一个问答对。

Agent 是什么？ReAct 模式是怎么工作的？

Agent 是能自主调用外部工具的 AI 智能体。大模型本身只能生成文本，不能执行实际操作。Agent 给模型配备了工具，让模型能调用外部函数获取真实数据。

ReAct = Reasoning + Acting，是一个循环过程：Thought（模型思考该做什么）→ Action（调用工具）→ Observation（观察工具返回结果）→ 循环直到收集到足够信息 → Answer（最终回答）。

项目用 LangGraph 的 createReactAgent 创建 Agent，定义了三个工具：getOrderInfo（查订单详情）、getLogisticsInfo（查物流轨迹）、getUserOrders（查用户订单列表）。每个工具用 Zod Schema 定义参数结构，description 告诉模型什么时候该用这个工具。

模型执行后返回一个 messages 数组，包含完整推理过程。后端从中提取 tool_calls 信息发给前端，前端展示"调用了什么工具、传了什么参数"的步骤卡片。

为什么 Agent 的 temperature 要设成 0？

因为 Agent 需要稳定的工具调用。temperature 越高，模型输出越随机。如果 temperature 很高，模型可能每次对同一个问题选择不同的工具，或者传错参数，导致工具调用失败。

项目中所有需要精确判断的场景都用了 temperature: 0——意图分类器、Agent、RAG Chain。需要灵活表达的场景用较高温度——基础对话用 0.5，通用闲聊用 0.7，答案整合用 0.5。

这是一个重要的工程经验：精确场景用低温度，灵活场景用高温度。

LangGraph 的 StateGraph 是怎么工作的？

StateGraph 是 LangGraph 的核心，用有向图编排工作流。包含几个概念：State 是在图中流动的共享数据，用 Annotation 定义，每个字段指定一个 reducer（合并策略）；Node 是处理步骤，接收 state 返回 state 更新；Edge 定义执行顺序；Conditional Edge 根据当前状态动态路由。

项目的图结构是钻石型：START → intentRouter → (orderAgent | ragNode | generalChat) → answerSynthesizer → END。intentRouter 节点用 LLM 做意图分类，返回 order/knowledge/general 之一。然后 routeByIntent 路由函数根据意图值决定走哪个分支。三个分支节点执行完后都汇聚到 answerSynthesizer 做答案整合。

流式输出用了 streamMode: 'updates'，每个节点执行完推送该节点的状态更新，前端就能实时显示"当前执行到哪个节点"的进度。还用了懒加载单例模式 getGraph()，图只编译一次，避免每次请求重新编译。

意图分类如果模型返回了意料之外的结果怎么办？

项目做了兜底处理。代码里定义了 VALID_INTENTS = ['order', 'knowledge', 'general']，模型返回的结果先用 trim().toLowerCase() 标准化，然后用 VALID_INTENTS.includes(intent) 检查。如果不在这个列表里，就 fallback 到 'general'，走通用对话节点。

这是生产级代码的防御性思维——永远不要完全信任模型的输出。即使 Prompt 里写了"只输出一个词"，模型也可能返回 "The intent is order" 这样的句子。做兜底处理比指望模型 100% 遵守 Prompt 可靠得多。

此外 temperature 设成 0 也降低了出错的概率，但并不能完全消除，所以兜底是必须的。

answerSynthesizer 节点为什么要单独做？不能让前面的节点直接返回答案吗？

这是关注点分离的设计。orderAgent 节点的 Prompt 明确写了"只查询数据，不需要生成最终的客服回答"，它只负责调用工具拿数据。答案整合统一由 answerSynthesizer 处理，它的 Prompt 会让回答保持一致的语气和格式。

这样做有几个好处：① 每个节点职责单一，便于维护和测试；② 统一的答案整合保证不同分支的回复风格一致；③ 如果以后要改回复格式，只需要改 answerSynthesizer 一个节点；④ orderAgent 返回的是结构化数据（包含 answer 和 steps），前端可以展示工具调用步骤，而 answerSynthesizer 返回的是用户友好的自然语言。

另外对 general 意图做了优化——generalChatNode 已经生成了答案，answerSynthesizer 直接透传，不重复调用 LLM，节省了 Token 消耗。

pgvector 和独立向量数据库（如 Pinecone、Milvus）相比有什么优劣？

优势：① 不需要引入新的基础设施，复用现有 PostgreSQL；② 可以在同一数据库中做向量检索和关系查询的联合查询；③ 事务一致性——向量和元数据在同一数据库中，可以保证数据一致性；④ 运维成本低，PostgreSQL 的备份、监控等工具都成熟。

劣势：① 向量检索性能不如专用向量数据库，特别是数据量到千万级时；② pgvector 的索引类型（IVFFlat、HNSW）调优比专用数据库复杂；③ 不支持分布式水平扩展，单机性能有上限。

选型建议：中小规模（百万级以下向量）选 pgvector 就够了，运维简单。大规模（千万级以上）或需要高性能检索的场景选 Milvus、Qdrant 等专用向量数据库。项目用 pgvector 是因为数据量小（两个 Markdown 文件），且学习者更容易搭建环境。

对话历史是怎么管理的？为什么不把全部历史都传给模型？

项目用滑动窗口管理历史——只取最近 10 条消息传给模型。原因有两个：① Token 限制，大模型有上下文窗口大小限制（如 DeepSeek 约 64K Token），历史太长会超限报错；② 成本控制，API 按 Token 计费，传的历史越长费用越高；③ 相关性，太早的对话通常对当前问题没有帮助，反而可能干扰模型。

前端 useChat.js 中用 messages.value.slice(-10) 截取最近 10 条。后端 formatHistory 函数把 { role, content } 格式转成 LangChain 的消息元组 ['human', content] 或 ['assistant', content]。

更高级的做法是用 LLM 做历史摘要——当历史超过一定长度时，用小模型把早期对话压缩成一段摘要，但这会增加额外的 LLM 调用开销。项目选择了简单有效的滑动窗口方案。

如果用户的问题同时涉及订单和知识库（比如"我的蓝牙耳机订单还没到，保修多久？"），你的意图路由会怎么处理？

这是当前架构的一个已知局限。意图分类器只返回一个分类，对于复合问题只能选其中一个方向处理。这个问题问得很好，说明你理解了条件路由的限制。

改进方案有几种：① 多意图分类：让分类器返回多个意图，然后并行执行 orderAgent 和 ragNode，两个结果都传给 answerSynthesizer 整合。LangGraph 支持 addConditionalEdges 返回多个节点名实现并行。② 多步推理：在图中加一个"问题拆分"节点，把复合问题拆成多个子问题，分别路由处理。③ 混合模式：让 Agent 同时拥有 RAG 检索能力——把知识库检索也封装成一个 Tool 给 Agent 调用，这样 Agent 可以自主决定先查订单还是先查知识库。

我倾向于方案③，因为它把路由决策交给 Agent 自主判断，比固定规则更灵活。但当前项目的分模块设计更适合教学演示，所以没有采用。

回答技巧：先承认局限，再给出改进方案，最后说明当前设计的选择理由。这展示了你对架构 trade-off 的理解。

前端是怎么解析 SSE 数据的？为什么不用 EventSource？

项目用的是 fetch + ReadableStream 而不是浏览器原生的 EventSource。原因是 EventSource 只支持 GET 请求，但本项目需要 POST（要传 message 和 history 参数）。所以用 Fetch API 手动读取流。

解析过程：response.body.getReader() 获取读取器 → decoder.decode(value, { stream: true }) 解码二进制为文本（stream: true 防止多字节字符截断）→ split('\\n') 按行分割 → filter(l => l.startsWith('data: ')) 过滤 SSE 数据行 → JSON.parse(line.slice(6)) 去掉 data: 前缀后解析 JSON。

解析出对象后按 type 字段或 content/done/error 字段分别处理。Vue 的响应式系统会自动触发 UI 更新，配合 nextTick 做滚动。

如果要让你优化这个项目，你会怎么做？

我会从几个维度优化：

性能：① RAG 查询改用流式（当前用 invoke 一次性返回），让答案逐字输出；② 给 pgvector 加 HNSW 索引加速检索；③ 用 Redis 缓存高频问题的回答。

准确性：① RAG 检索加 rerank（重排序），用 Cross-Encoder 对初步检索结果做二次排序提升精度；② 意图分类改用 fine-tuned 小模型替代 LLM，降低延迟和成本；③ 加 query rewriting——把用户的口语化问题改写成更适合检索的关键词。

架构：① 支持多意图并行处理，解决复合问题；② 加 Human-in-the-loop——订单退款等敏感操作需要人工确认；③ 把 Mock 数据换成真实数据库；④ 加日志和监控，追踪每个节点的耗时和 Token 消耗。

前端：① 加 Markdown 渲染支持（当前纯文本）；② 加对话导出功能；③ 加打字音效和主题切换；④ 用 Web Worker 处理 SSE 解析避免阻塞主线程。

回答技巧：从多个维度回答，展示全局视野。每个点不用展开太多，点到为止，等面试官追问再深入。
